# Phase 1 Hunt — wazuh-rules/target_rules.xml and wazuh/active-response/*

Scope: `wazuh-rules/target_rules.xml`, `wazuh/active-response/lock-account.sh`,
`wazuh/active-response/kill-session.sh`, `wazuh/active-response/bruteforce-guard.sh`,
`wazuh/active-response/idor-guard.sh`. Cross-referenced against
`wazuh/config/wazuh_cluster/wazuh_manager.conf` (AR bindings) and `target/routes/admin.py`
/ `target/logging_middleware.py` (data provenance for fields the rules/scripts consume)
where needed to establish exploitability/severity. K3 (curl exit code / HTTP status never
checked in lock-account.sh and kill-session.sh) is already known and not re-listed below
except where a *different* mechanism in the same file is involved.

| File | Severity | Summary | Line(s) | Suggested fix |
|---|---|---|---|---|
| `wazuh/active-response/kill-session.sh` + `wazuh/config/wazuh_cluster/wazuh_manager.conf` | **Critical** | `kill-session` is bound directly to rule `100102` via a real `<active-response>` block (`wazuh_manager.conf:299-303`), so execd dispatches it directly, the same invocation path as `bruteforce-guard.sh`/`idor-guard.sh`. Those two scripts explicitly switched from `INPUT_JSON=$(cat)` to `IFS= read -r INPUT_JSON` because (per their own header comments, and empirically confirmed via `/proc/<pid>/task` during Task 8 verification) wazuh-execd on this Wazuh 4.9.2 build writes the AR JSON payload but never closes/EOFs the child's stdin, so `$(cat)` hangs forever. `kill-session.sh` still uses `INPUT_JSON=$(cat)` (line 22) and was never updated. The script's own comment in `bruteforce-guard.sh` (line 89-92) asserts "(lock-account.sh/kill-session.sh don't hit this: they're invoked here via a plain `echo ... \| script` pipe...)" — true for `lock-account.sh` (whose direct `<active-response>` binding was deliberately removed, `wazuh_manager.conf:234-240`) but **false for `kill-session.sh`**, which retains a live, execd-dispatched binding. Net effect: every real command-injection alert (100102) causes execd to spawn `kill-session.sh`, which blocks forever on `cat` and never reaches the `jq`/`curl` lines at all — the kill-session response for command injection silently never executes, and a hung subprocess accumulates per attack. | `kill-session.sh:22`; binding at `wazuh_manager.conf:299-303` | Change `INPUT_JSON=$(cat)` to `IFS= read -r INPUT_JSON` (matching the fix already applied in `bruteforce-guard.sh`/`idor-guard.sh`), or remove the direct `<active-response>` binding and route kill-session only through a proxy script the way `lock-account.sh` was reworked. |
| `wazuh/active-response/lock-account.sh`, `wazuh/active-response/kill-session.sh` | Medium | Neither script sets `set -eu` (or any error trap) at all — `bruteforce-guard.sh` and `idor-guard.sh` both do. This is broader than K3 (which is specifically about curl's exit code / HTTP status): with no `set -eu`, *any* upstream failure — `jq` erroring on a malformed/non-JSON `INPUT_JSON`, `cat` failing, etc. — is silently swallowed and the script falls through to the final `curl` line with empty/garbage variables, exiting 0 regardless. | `lock-account.sh:1` (no `set` line); `kill-session.sh:1` (no `set` line) | Add `set -eu` to both, and explicitly handle the case where `jq` fails to parse `INPUT_JSON` (e.g. `|| exit 1` after the `jq` extraction) rather than relying on `select()` output being merely empty. |
| `wazuh/active-response/bruteforce-guard.sh`, `wazuh/active-response/idor-guard.sh` | High | The counting `jq` pipeline (`tail -n "$TAIL_LINES" "$REQUEST_LOG" 2>/dev/null \| jq ... 2>/dev/null \| wc -l \| tr -d ' '`) has no error checking on the pipeline as a whole, and POSIX `/bin/sh` (dash) has no `pipefail` — the assigned exit status is only `tr`'s, which is always 0. If `jq` hits a malformed/non-JSON line anywhere in the tailed window (or `tail`/the log file itself is transiently unreadable), it errors out mid-stream; any matches already emitted before the error are kept but everything after is lost, and the failure is invisible (`2>/dev/null` on both `tail` and `jq`, no `|| exit 0`/`|| exit 1` guard as is used one code block earlier for `EVENT_EPOCH`). This can silently **undercount** a genuine 5-in-window brute-force/IDOR burst to fewer, causing the script to exit 0 (no action) even though the real count met the threshold — the same "claims success/no-action regardless of actual outcome" class K3 already flagged for curl, recurring here in the detection-counting logic itself rather than in the response dispatch. | `bruteforce-guard.sh:127-134`; `idor-guard.sh:196-202` | Capture jq's own exit status explicitly (e.g. run the jq stage separately and check `$?`, or use `set -o pipefail` if the shebang is changed to bash) and fail loud/log rather than silently returning a possibly-partial count. |
| `wazuh/active-response/idor-guard.sh` | High | On the block path, the "inserting DROP" line is appended to `active-responses.log` (line 230) *before* the `iptables -I INPUT`/`iptables -I FORWARD` calls run (lines 231-232), and neither `iptables` call's exit status is checked. Because `set -eu` is active, if `iptables -I INPUT ...` fails (invalid `$SRCIP` format, missing capability, chain absent, etc.) the script aborts immediately — after the log line already claims the DROP was inserted, before the FORWARD rule is attempted, and before the STATE_FILE counter is incremented (lines 239-245, never reached). Net result: `active-responses.log` records a successful block that may not exist, while the counter/lock-state bookkeeping the "delete" path depends on is left at its prior value — the same "reports success regardless of outcome" class as K3, applied to the audit log instead of curl. | `idor-guard.sh:216-232` | Move the log line after both `iptables -I` calls succeed (or log on both attempt and confirmed success), and check each `iptables -I` exit code explicitly before treating the block as real / incrementing the counter. |
| `wazuh/active-response/idor-guard.sh` | Low (race, self-correcting) | The threshold-crossing decision-and-block section (lines 177-232: read timestamp, count, `iptables -I` x2) is **not** protected by the per-IP `flock` — only the STATE_FILE counter increment afterward (lines 239-245) is. Because execd can and does dispatch multiple "add" invocations for the same source IP in quick succession (documented in this file's own header as empirically observed — "4 duplicate DROP rules from a single burst"), several concurrent above-threshold invocations for the same IP can each independently run `iptables -I` and each increment the counter by one, producing N redundant duplicate INPUT/FORWARD DROP rules and a counter of N. This is not a permanent-stuck-block bug (Wazuh dispatches exactly one "delete" per "add", so all N inserts get reversed by N matching deletes — confirmed by the file's own header re: 1:1 add/delete dispatch), but it is a real, undocumented race distinct from the one already fixed in Fix Round 2 (which only covers the counter's read-modify-write, not the decision-to-block itself). | `idor-guard.sh:177-232` (compare to the flock scope at 239-245 and 154-168) | If exact-once insertion matters, take the per-IP `flock` earlier, around the count-then-insert decision itself, not just around the counter update. |
| `wazuh/active-response/kill-session.sh` vs `wazuh/active-response/lock-account.sh` | Low | `lock-account.sh` was explicitly hardened (per its own "Final-review fix (finding #6)" comment) to use `curl --data-urlencode "username=${USERNAME}"` instead of raw `-d` interpolation, specifically to avoid unescaped `&`/`=` in an attacker-influenced value being reinterpreted as extra form fields. `kill-session.sh` still uses the un-hardened form: `curl -s -X POST ... -d "user_id=${USER_ID}"` (line 29). Today `USER_ID` is sourced from `data.user_id`, which `target/logging_middleware.py` populates from `session.get("user_id")`, itself set in `target/routes/admin.py:52` from a SQLite integer primary key (`row["id"]`) — so under the current schema it can't practically contain `&`/`=`. The inconsistency is still worth flagging: the same class of bug the reviewer explicitly fixed in the sibling script was left unaddressed here, so if `user_id`'s provenance ever changes (e.g. a non-integer identifier, or the field is ever sourced from something more attacker-adjacent), the same unescaped-injection gap reopens silently. | `kill-session.sh:29` | Switch to `--data-urlencode "user_id=${USER_ID}"` for consistency/defense-in-depth, matching `lock-account.sh`. |
| `wazuh/active-response/idor-guard.sh` | Ambiguous / not confirmed exploitable | `STATE_FILE="$STATE_DIR/$SRCIP"` and `LOCK_FILE="$STATE_DIR/$SRCIP.lock"` interpolate `$SRCIP` directly into a filesystem path with no format validation (no check that it looks like an IPv4/IPv6 address, no rejection of `/`, `..`, or other path-breaking characters). Under the current `target/logging_middleware.py`, `srcip`/`remote_addr` come straight from Flask's `request.remote_addr` (raw WSGI/TCP peer address, not read from any client-controlled header — no `ProxyFix`/`X-Forwarded-For` trust found in the target app), so this is not exploitable as-is. Flagging as ambiguous/defense-in-depth: if the stack ever gains a reverse proxy that maps a spoofable header into `remote_addr`, or `remote_addr` takes an unusual representation (e.g. `::ffff:`-mapped or scoped IPv6 literals containing `%`), this becomes a path-traversal-flavored arbitrary file path under `/tmp`. | `idor-guard.sh:118, 138, 154, 239` | Validate `$SRCIP` against a strict IPv4/IPv6 shape before using it in any path or `iptables` call; reject/exit quietly otherwise. |
| `wazuh-rules/target_rules.xml` | Medium / ambiguous | Rule `100103` (the real, now-live base alert that `bruteforce-guard.sh` is bound to) requires `status_code == 200` on the `/admin/login` POST. The Sigma source it was translated from (`docs/sigma-rules/bruteforce-admin-login.yml`) titles this "**Repeated Failed** Admin Login Attempts" and describes it as detecting failed attempts — but `target/routes/admin.py`'s `/admin/login` handler returns HTTP 200 for both the failure path (`render_template_string(LOGIN_FORM, error="Invalid credentials")`, line 50) and the success path (line 54) — Flask defaults both to status 200; there is no distinct failure status code in this app. So the `status_code==200` condition can't actually distinguish "failed" from "successful" login attempts here — it happens to be true for literally every login POST regardless of outcome, which incidentally makes the counting logic work for the lab's actual brute-force scenario, but the field is misleading relative to its Sigma-derived intent and origin comment, and would silently break (only ever match the successful-login case) if this route were ever changed to return proper HTTP semantics (e.g. 401 on bad credentials). Not a functional bug against the current app, but a real mismatch between documented intent and actual match condition worth flagging as ambiguous. | `target_rules.xml:141-150`; compare `docs/sigma-rules/bruteforce-admin-login.yml:1,4-7,15`; `target/routes/admin.py:49-54` | Either drop the `status_code` field (it's a no-op given the app's current behavior, so it adds false confidence) or, if the app is ever given real failure status codes, explicitly decide whether brute-force counting should key off failures, successes, or all attempts, and update rule/comment/Sigma source together. |
| `wazuh-rules/target_rules.xml` | Low | Rule `100101` (SQLi on `/search`) includes a bare `--` as one of four regex alternatives: `(?i)('\s*OR\s*'1'='1\|'\s*OR\s*1=1\|--\|UNION\s+SELECT)`. Unlike the other three alternatives, `--` requires no surrounding context (no preceding quote, no keyword) and will match any `q` value containing two consecutive hyphens anywhere — e.g. date ranges ("2024--2025"), CLI-style flags typed into a search box, markdown/em-dash-style text, email signature blocks ("-- \n"). Given this rule is level 12 (a real, immediately-actionable alert with no aggregation/threshold), an overly broad match here has a meaningfully higher false-positive cost than the same over-breadth would in an aggregated rule. | `target_rules.xml:113` | Require `--` to be adjacent to other SQL syntax (e.g. `'--` or `--\s*$`) rather than matching it as a bare, context-free two-character substring. |
| `wazuh-rules/target_rules.xml` | No finding (checked) | Rule ID collisions: only one rule file exists in the repo (`wazuh-rules/target_rules.xml`); IDs 100100-100106 are unique within it and fall inside Wazuh's reserved local custom range (100000-119999) with no collision against any other ruleset file found in the repo. | — | — |

## Notes on what was intentionally *not* re-filed

- `lock-account.sh`/`kill-session.sh` never checking `curl`'s exit code or the target's HTTP
  status — this is K3, already in the ledger, not re-listed here except where a genuinely
  different mechanism in the same files was found (the `kill-session.sh` execd-hang bug above,
  the missing `set -eu` above, and the `idor-guard.sh` log-before-action bug above are all
  distinct from K3's specific "never checks curl" claim, even though they're the same broad
  *class* of "reports success/no-action regardless of actual outcome").
- Rules 100104/100106 (the dead `if_matched_sid`/`frequency` rules that never fire on this
  Wazuh 4.9.2 build) are not re-flagged as a new finding — the file's own header already
  documents this exhaustively as an investigated, resolved-by-design-change issue, and the
  rules are explicitly marked as vestigial/documentation-only, not live detection logic.
