# Phase 1 Hunt -- Code Review: blue_agent/

Scope: `blue_agent/` only (config.py, loop.py, tools.py, http_tool.py,
ollama_client.py, state.py, wazuh_alerts.py, main.py, tests/). K2
(unguarded `json.loads(args)` in tools.py) and K4 (ReAct loop never
observed live) are already tracked in the findings ledger and are not
re-reported here, though several findings below compound directly into
K4's live-verification gap.

| Severity | Summary | File:line | Suggested fix |
|---|---|---|---|
| HIGH | `WazuhAlertsReader.poll_new_alerts()` tracks position purely as a line **count** (`self._lines_read`), never a byte offset/inode check. If `alerts_log_path` is ever rotated/truncated by the host (log rotation, a fresh Wazuh install, disk cleanup) so the file becomes shorter than the previous read count, `complete_lines[self._lines_read:]` silently returns `[]` forever -- Python slicing past the end of a list raises nothing, so this never surfaces as an error. The agent keeps heartbeating and looks healthy while it has permanently stopped seeing new alerts. This is the same "claims success / looks fine but isn't" failure class already called out for K3/K6. | `blue_agent/wazuh_alerts.py:26-27` | Track `(inode, byte_offset)` or detect `path.stat().st_size < last_size` / a changed inode and reset `_lines_read = 0` when the file has shrunk. |
| HIGH | `BlueAgentState.record_finding()` is fully implemented and unit-tested (`tests/test_state.py`), but it is **never called from the production code path**. `tools.py`'s `escalate_response` branch only calls `state.log_event(...)` (event log), not `state.record_finding(...)` (persisted memory). The "hold" branch in `loop.py` doesn't call it either. Since `append_memory_entry` is therefore never invoked in the live loop, `blue_memory.json` is never written, so `recall_past_findings` / `recall_summary()` always returns empty and the system prompt's instruction ("Use recall_past_findings ... to avoid repeating what you've already decided") is a no-op across every run. This is exactly the kind of gap K4 flags as unverified -- it only shows up once you trace the live call path, not in isolated unit tests. | `blue_agent/state.py:17-19` (defined), `blue_agent/tools.py:68` (only `log_event`, no `record_finding` call), `blue_agent/loop.py` (no call site at all) | Call `state.record_finding(...)` from the `escalate_response` dispatch (and optionally from the "hold" reasoning branch) so cross-run memory is actually populated. |
| HIGH | In `run()`, after the `ollama.chat()` call succeeds without raising, `assistant_message = response["message"]` is assigned inside the guarded `try`, but the following lines that call `.get(...)` on it (`assistant_message.get("tool_calls")`, `assistant_message.get("content", "")`) run **outside** the try/except. If Ollama returns a 200 response whose `"message"` value is present but not a dict (e.g. `null`, a string, or a different shape from a model/template change), `.get()` raises an uncaught `AttributeError` that is not `requests.RequestException` or `KeyError`, so it is not caught by the existing `except (requests.RequestException, KeyError)` block. This propagates out of `run()` -- and `main.py` has no surrounding try/except -- killing the entire blue-agent process for the round with no further heartbeats and no `ollama_error` event logged. Existing tests only cover "message" key missing entirely and tool_calls missing "function", not "message" present-but-wrong-type. | `blue_agent/loop.py:86,93,95` ; `blue_agent/main.py:5-7` (no top-level guard) | Broaden the except clause (or validate `isinstance(assistant_message, dict)` before use) and log an `ollama_error` instead of letting it propagate; consider wrapping `run()`'s main loop body in a broader per-iteration try/except so one malformed response can't end the whole round. |
| MEDIUM | The `messages` list passed to `ollama.chat()` grows every iteration that has new alerts (new alert message + assistant reply + tool result(s)) and is never trimmed, summarized, or capped. With `max_iterations` defaulting to 200 and a noisy round, the full growing transcript is re-sent on every single turn, so token count/latency increase monotonically and can exceed the model's context window well before iteration 200 -- exactly the untested "long, real, alert-heavy round" scenario K4 calls out. | `blue_agent/loop.py:56-103` | Cap history length (e.g. keep last N turns plus the system prompt) or periodically summarize older turns into the persisted memory instead of keeping raw messages forever. |
| MEDIUM | `escalate_response`'s `target` argument is forwarded verbatim into the internal endpoint's POST body (`data={field: target}`) with no type/format check per action (e.g. nothing stops a non-numeric string being sent as `user_id` for `kill_session`, or an oversized/odd-charset string for `username`/`source_ip`). Validation is entirely delegated to the LLM's judgment and to the downstream `/internal/*` endpoint, with no defense-in-depth on the blue_agent side even though `target` is ultimately derived from alert data that can reflect attacker-influenced input. | `blue_agent/tools.py:56-68` | Add a light per-action format check (numeric for `kill_session`, IP-shaped for `block_ip`, safe username charset for `lock_account`) before issuing the HTTP call, returning a tool-error result instead of forwarding blindly. |
| LOW | `poll_new_alerts()` reads and re-parses the **entire** alerts file from byte 0 on every poll (`f.readlines()` over the whole file), discarding everything before `_lines_read` each time. This is O(total file size) per poll rather than an incremental/seek-based read, so cost grows with alerts.json size over a long-running round -- compounds with the rotation issue above (finding is both a perf concern and part of why the module doesn't tolerate a shrinking file). | `blue_agent/wazuh_alerts.py:15-16` | Use `file.seek()`/track byte offset instead of re-reading all lines each poll. |

## Notes on things checked but NOT flagged

- `ollama_client.py`'s `resp.json()` decode-error path: with the pinned
  `requests>=2.31` (`requirements.txt:2`), `resp.json()` failures raise
  `requests.exceptions.JSONDecodeError`, which **is** a subclass of
  `requests.RequestException` in this requests version, so it is already
  caught by `loop.py`'s existing `except (requests.RequestException, KeyError)`.
  Confirmed not a gap.
- `HttpTool.request`'s own `except requests.RequestException` catch and
  `config.py`'s env-var parsing (`int()`/`float()` raising at startup on bad
  input) were reviewed and look intentional/acceptable (fail-fast at
  startup vs. silent swallow at runtime).
